# Passive Swarm Telemetry

Swarm Telemetry measures activity, throughput, token use and provider cost across peers, sessions, agents, work, providers and harnesses. Its collection target is all accounts and all services: all Slack and GitHub contents and activity, all machine and cloud activity, and the source histories of every other discovered service. Discovery uses existing credential references, installed connectors, configuration and observability inventories. Starter services and configured roots are discovery seeds, never a boundary on the corpus. Every discovered source keeps an explicit reader, cursor and coverage state; a service without a bound reader remains in the recovery inventory. It does not run the work it observes. [SWARM_THROUGHPUT_POLICY.md](SWARM_THROUGHPUT_POLICY.md) states the shared access and execution policy.

The baseline is Python standard library code under [integrations/swarm_telemetry](../integrations/swarm_telemetry/README.md). SQLite stores events and notification state. Collectors adapt available source records; they retain original IDs and source links. The runner can ingest and report through its documented commands. Collection is incremental and deduplicated. A source that cannot be read retains its cursor and failure state for recovery. Missing data stays missing; it is never silently counted as zero or presented as complete swarm coverage.

An event identifies its source and source ID, event ID, occurrence and observation times, event type, peer, session, agent and parent agent, provider, model, harness, work and operation IDs, status, summary, source URL, metrics and metadata. Unknown identities remain unknown. Observation time records when the collector saw an event; occurrence time records the source's event time. A delayed source event keeps both. Mirrors preserve an original event ID so the same event does not create several notifications.

Metrics preserve their basis. Observed values come from a usage response, service record or supplied event measurement. Declared values come from a peer or source's reported value. Estimated values carry their formula and pricing basis when available. A field without a supplied value is unavailable. These labels describe how a value entered the record; they do not change the event narrative. Keep input, output and cached tokens distinct. Do not add overlapping usage snapshots or treat a provider-wide balance as a single session's cost. Monetary totals retain currency, period and coverage. Missing provider costs do not become `$0`.

Notifications use a deterministic baseline. Supported events include merges, artifact and result availability, dependency changes, rate limits and service recovery, owner instructions, handoffs, answers to explicit requests, imminent renewals, owner signatures, new money commitments and urgent items. Unknown event kinds remain stored events without inventing an alert. Routine authorized token use is not a new money commitment. Existing metadata can identify affected peers, channels and work references; the baseline neither discovers a new provider nor dispatches work to those audiences.

Each notification has `notification_id`, `event_id`, `work_id`, `type`, `severity`, `title`, `body`, `occurred_at`, `source_refs`, `audience`, `supersedes`, `status` and `metadata`. A stable notification ID derives from the original event ID. Mirror source references and affected audiences are merged. Resolution events carry `resolves_event_ids` or `supersedes`; the original update becomes resolved and records its resolving notification. This preserves useful changes while avoiding repeated stale blocker notices. Notifications require no acknowledgment.

Jev enrichment is optional and asynchronous. An independent authorized integration can submit an enrichment request and later provide its available answer. `enrich_available` adds that context to metadata. Baseline ingest and notification generation never import a Jev client, retrieve a key, call Jev, wait for a response or select a provider. An absent, pending or failed enrichment leaves the baseline usable. Enrichment cannot alter notification identity, audience, severity, resolution or owner authority.

Delivery is optional and uses the existing service roads. An adapter receives a redacted notification and returns the actual provider result. No credentials or message sends are part of the baseline. The durable outbox writes its sending state before a callback and preserves a stable notification ID across retries. A definite failure can retry. A timeout, exception, unknown result or interrupted send becomes uncertain and needs provider readback before replay. Confirmed delivery retains its receipt. Existing operation IDs and provider idempotency remain the means to prevent duplicate or conflicting operations; there is no new approval or access gate.

Preserve complete source envelopes in authenticated encrypted custody before creating redacted operational projections. Source custody uses no sampling, body truncation or replacement of original content with a summary. Transcripts and raw file ranges retain their original bytes; native connector responses retain their complete envelopes. Provider-side omissions, unavailable history, nonterminal pagination and pending cloud custody remain explicit unread regions. A successful read of one connected account never establishes coverage of another account of the same service. Keep private originals out of authored posts, operational logs and notification bodies. Structured secret fields and recognized credential formats are scrubbed from projections and delivery. Secret references identify the existing shared credential facility without copying secret values into dashboards. Every peer retrieves the custody key directly using the shared reference `telemetry/source-custody-key`.

Source pages and ingestion batches are resumable collection work. They do not limit the corpus or impose a swarm throughput policy. Indexed overview groups count every recorded source partition; detailed source lists use explicit continuation cursors. The collector reports local storage pressure separately and preserves unread checkpoints when its own storage cannot accept further backfill. Dashboard reads, account discovery, runtime census and swarm execution remain independent. Cloud and remote-machine sources need their actual authenticated read and custody roads; references awaiting those roads remain pending until their full source is captured.

Peer and channel updates are internal passive notifications. Owner email attention is for signatures, new money commitments outside existing authorization, or urgent items. It never turns ordinary work into an owner approval queue. The no-contact hold, Bryce's exact approval of personal meeting commitments, and the central private TJLabs incident reporting road remain in force across notifications, delivery adapters and enrichment. Measurement never limits a peer's access or throughput.

Run the implementation on real available records and inspect the command exit code and output. The current swarm rules prohibit new tests, fixtures, mocks and workflows. Runtime results establish the behavior actually exercised; available coverage and source freshness remain explicit in the output.
