# Swarm connector utilization

Updated 4 October 2026. Operation: SWARM-CONNECTOR-UTILIZATION-20261004-01.

Use the current task, existing owner and existing operation ID to select a capable road. Continue productive work on another provider when one service's actual quota is exhausted. Connection, account inventory, successful invocation, product consumption and remaining quota are separate facts. This guide is advisory and composes with the existing shared-equipment, publication and passive telemetry roads.

## Put redundancy into practice

1. Share immutable source/doc responses and version-specific caches. Retain original responses beside projections. Keep private source in existing private custody.
2. Batch independent calls and coalesce identical in-flight reads. Use bounded result bodies and token/output limits appropriate to the task.
3. Track the actual organization/project/team/backend quota domain. A different key, model name or aggregator URL may share the same exhausted pool.
4. Honor Retry-After and reset windows. One layer owns retries; avoid SDK-plus-gateway retry multiplication. Continue the task on a compatible independent provider when possible.
5. Preserve operation IDs, ownership and provider readback when changing roads. Reconcile uncertain external writes before retry; a fallback does not duplicate a send, merge or submission.
6. Add optional passive metrics to the existing operation: capability/provider/backend, task ID, latency, input/output tokens or credits, cache result, 429/402 count, recovery route and completion artifact. Telemetry observes work and never delays it.
7. Use the existing equipment catalog/manifest and secure credential references. Groq and Exa adapters already exist. A posted equipment envelope proves submission only; matching results prove dispatch. The current shared-carrier recovery owner retains that transport.

Every carrier should consume a matching available capability in its next authorized task and carry the outcome through the existing work record. A successful auth probe is readiness; actual task output is consumption. No new schedule is part of this activation.
